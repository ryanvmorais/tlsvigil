# 002 — Certificate check — design

## Overview

One new module, `src/tlsvigil/certificate.py`, holds the whole check. `check_certificate(host,
port)` validates its inputs, opens one TCP connection with `socket.create_connection`, wraps it
with an `ssl.SSLContext` built by `create_context()`, and lets the handshake verify the chain and
the name. Every way the attempt can end is turned into a `CertificateResult` value: a verified
certificate with its expiry date and days left, an `invalid` one with the reason taken from the
OpenSSL verification code, or an `error` with the kind of failure. The function never raises for a
network or TLS failure, and it never opens a second connection. A separate pure function,
`classify(result, warn_days)`, turns a result into `ok`, `expiring`, `invalid` or `error`, so the
threshold, which belongs to the configuration of spec `004`, stays out of the network code.

The context is built explicitly instead of trusting the defaults of the running Python, because
those defaults changed in 3.13 (ADR-2). The tests never reach a real network: an autouse fixture
refuses any resolution or connection outside the loopback interface (ADR-5), and a small threaded
server on `127.0.0.1` serves certificates made during the test with `trustme` (ADR-4).

## Data model

```python
class Outcome(StrEnum):          # what the handshake gave
    VERIFIED = "verified"
    INVALID = "invalid"
    ERROR = "error"

class Status(StrEnum):           # what classify() gives (RF-02)
    OK = "ok"
    EXPIRING = "expiring"
    INVALID = "invalid"
    ERROR = "error"

class InvalidReason(StrEnum):    # RF-03
    EXPIRED = "expired"
    NOT_YET_VALID = "not_yet_valid"
    HOSTNAME_MISMATCH = "hostname_mismatch"
    UNTRUSTED = "untrusted"
    OTHER = "other"

class ErrorKind(StrEnum):        # RF-04
    DNS = "dns"
    REFUSED = "refused"
    TIMEOUT = "timeout"
    TLS = "tls"
    OTHER = "other"

@dataclass(frozen=True, slots=True)
class CertificateResult:
    host: str
    port: int
    checked_at: datetime                 # aware, UTC: the time the days are counted from
    outcome: Outcome
    not_after: datetime | None = None    # VERIFIED only
    days_left: int | None = None         # VERIFIED only, >= 0
    issuer_organization: str | None = None
    issuer_common_name: str | None = None
    reason: InvalidReason | None = None  # INVALID only
    error_kind: ErrorKind | None = None  # ERROR only
    message: str | None = None           # INVALID and ERROR: the library's text, as read
```

`StrEnum` values are the strings the JSON output of spec `004` will print, so no mapping table is
needed there. The result is frozen: later specs read it and never change it.

## Components

### Input validation (RF-06)

`_validate(host, port, timeout, now)` runs before any socket exists and raises `ValueError` with a
message that names the bad argument. The host is refused when it is empty, has leading, trailing or
inner whitespace, contains `://`, `/`, `[`, `]` or `@`, or contains `:` without being an IPv6
address (`ipaddress.ip_address` parses it). The port must be an `int` (not a `bool`) from `1` to
`65535`; the timeout a number greater than `0` (not a `bool`); `now`, when given, an aware
`datetime` (a naive one would make the days left depend on the machine's time zone).

### The context (RF-05, RNF-02; ADR-2, ADR-7)

`create_context()` returns `ssl.create_default_context()` (system trust store, `CERT_REQUIRED`,
`check_hostname = True`) with these set explicitly on every Python version:

| Setting | Value | Why |
|---|---|---|
| `minimum_version` | `TLSVersion.TLSv1_2` | RF-05; the default since 3.10, pinned so it cannot drift |
| `verify_flags` | defaults minus `VERIFY_X509_STRICT` and `VERIFY_X509_PARTIAL_CHAIN` | the 3.12 verification on 3.13+ too (ADR-2) |
| `hostname_checks_common_name` | `False` | browsers ignore the subject common name; only the SAN counts |

### The check (RF-01, RF-03 to RF-05; ADR-1, ADR-3, ADR-6)

```text
validate → now = now or datetime.now(UTC)
create_connection((host, port), timeout)            ── gaierror → ERROR dns
                                                    ── ConnectionRefusedError → ERROR refused
                                                    ── TimeoutError → ERROR timeout
                                                    ── other OSError → ERROR other
context.wrap_socket(sock, server_hostname=host)     ── SSLCertVerificationError → INVALID, reason
   (the handshake runs here, with the same timeout)  ── TimeoutError → ERROR timeout
                                                    ── other SSLError or OSError → ERROR tls
getpeercert() → notAfter, issuer                    ── no notAfter → ERROR other
both sockets closed by their context managers in every branch
```

- **One connection.** `create_connection` tries each address of the name in turn until one
  accepts, as a browser does; the certificate checked is the one of the first address that
  accepts. Nothing is retried after a failed handshake.
- **SNI and IP addresses.** `server_hostname=host` sends the name in the handshake and makes the
  hostname check use it; for an IP address Python sends no SNI and matches the address against the
  IP entries of the SAN (RF-05).
- **No application data.** After the handshake the function reads the peer certificate and leaves
  the `with` blocks; nothing is written to the socket.
- **Days left.** `not_after = datetime.fromtimestamp(ssl.cert_time_to_seconds(cert["notAfter"]),
  UTC)`; `days_left = max(0, (not_after - now) // timedelta(days=1))`. Rounding down gives `0` in
  the last 24 hours (RF-01); the `max` only matters when a test gives a `now` later than the
  expiry of a certificate the system clock still accepts.
- **Issuer.** The first `organizationName` and the first `commonName` of `cert["issuer"]`, as the
  strings `ssl` decoded, or `None` (RNF-03).

### Verification reasons (RF-03; ADR-3)

`SSLCertVerificationError.verify_code` (the OpenSSL `X509_V_ERR_*` number) picks the reason;
`verify_message` becomes `message`.

| Code | OpenSSL name | Reason |
|---|---|---|
| 10 | `CERT_HAS_EXPIRED` | `expired` |
| 9 | `CERT_NOT_YET_VALID` | `not_yet_valid` |
| 62, 64 | `HOSTNAME_MISMATCH`, `IP_ADDRESS_MISMATCH` | `hostname_mismatch` |
| 2, 18, 19, 20, 21 | `UNABLE_TO_GET_ISSUER_CERT`, `DEPTH_ZERO_SELF_SIGNED_CERT`, `SELF_SIGNED_CERT_IN_CHAIN`, `UNABLE_TO_GET_ISSUER_CERT_LOCALLY`, `UNABLE_TO_VERIFY_LEAF_SIGNATURE` | `untrusted` |
| any other | — | `other` |

An expired intermediate also gives code 10, so `expired` covers the chain, not only the leaf; the
message is the same and names no depth.

### Classification (RF-02; ADR-1)

`classify(result, warn_days)` raises `ValueError` for a negative or non-`int` threshold, returns
`INVALID` or `ERROR` for those outcomes, and for a verified result returns `EXPIRING` when
`days_left < warn_days`, `OK` otherwise. A threshold of `0` therefore never warns by date.

### Test harness (RF-07; ADR-4, ADR-5)

- **Network guard** (`tests/conftest.py`, autouse). It wraps `socket.getaddrinfo` and
  `socket.socket.connect` / `connect_ex` with `monkeypatch`. Resolution is allowed for
  `localhost` and for IP literals; a connection is allowed only to `127.0.0.0/8` and `::1`.
  Anything else raises `NetworkAccessError`, a subclass of `AssertionError` that names the
  address, so the check under test, which catches `OSError` only, cannot turn it into an `error`
  result: the test fails. `socket.create_connection`, `ssl`, `http.client` and `urllib` all go
  through these two calls, so specs `003` and `005` inherit the guard.
- **`LocalServer`** (`tests/tls_server.py`). A context manager that binds `127.0.0.1:0`, accepts in
  a daemon thread, and per connection either completes a TLS handshake with a given server context
  and closes (`tls`), accepts and stays silent (`silent`), or writes a plain-text HTTP line and
  closes (`plain`). The thread swallows and records its own exceptions (a client rejecting the
  certificate is the normal case), so `filterwarnings = ["error"]` sees no unhandled thread
  exception; `__exit__` closes the listening socket and joins the thread.
- **Fixtures.** `ca` is a fresh `trustme.CA()` per test; `client_context` is `create_context()`
  plus `ca.configure_trust(...)`, so the tests run the real context with one extra trust anchor;
  `serve` starts a `LocalServer` for a `trustme` leaf, with the full chain or the leaf only (the
  leaf-only PEM is written to `tmp_path`).
- **`tests/certs.py`** builds, with `cryptography`, the two certificates `trustme` does not offer: a
  self-signed leaf with a SAN, and a leaf signed by the test CA without an Authority Key Identifier
  (valid, but refused by `VERIFY_X509_STRICT`).

## Interfaces

Python only; no command, file or network contract changes for the user (resolved decision 1 of
the requirements).

```python
def create_context() -> ssl.SSLContext: ...

def check_certificate(
    host: str,
    port: int = 443,
    *,
    timeout: float = 10.0,
    now: datetime | None = None,
    context: ssl.SSLContext | None = None,
) -> CertificateResult: ...

def classify(result: CertificateResult, warn_days: int) -> Status: ...
```

`context` exists so that the tests can add a trust anchor; `None` means `create_context()`. The
names exported are the three functions, `CertificateResult` and the four enums.

## ADRs

### ADR-1 — The check returns a value, and the threshold is applied by a separate function

**Decision.** `check_certificate` returns a `CertificateResult` for every outcome of the network
and the TLS library and raises only `ValueError` for bad input; `classify` applies the threshold.
**Alternatives.** (a) Raise one exception per failure kind and let the caller catch them. (b) Pass
`warn_days` to the check and return the status directly.
**Why.** A monitor checks many hosts and must report each one; exceptions would push the
"never a silent pass" rule (requirements, resolved decision 2) onto every caller. Keeping the
threshold out makes the classification a pure function, tested at its boundaries without a
socket, and lets spec `004` change thresholds without touching the network code.
**Trade-off.** A caller can forget to look at `outcome`; the frozen type with `None` fields per
outcome and `classify` as the one way to a status make that unlikely.

### ADR-2 — Verification settings are explicit, at the Python 3.12 behaviour

**Decision.** `create_context()` clears `VERIFY_X509_STRICT` and `VERIFY_X509_PARTIAL_CHAIN`,
sets the minimum to TLS 1.2 and turns off the common-name fallback, on every Python version.
**Alternatives.** (a) Inherit the defaults of each Python. (b) Turn `VERIFY_X509_STRICT` on
everywhere (the 3.13 default).
**Why.** Python 3.13 added both flags to `create_default_context()`, so (a) gives a different
verdict for the same certificate on 3.12 and 3.13 (RNF-02). Strict mode rejects certificates that
browsers accept (a leaf without an Authority Key Identifier, a CA without a critical basic
constraint); the warning should mean "clients will fail", not "a stricter-than-browser profile
fails", so (b) would raise alarms nobody can act on. Partial chains would let an intermediate in
the trust store end the chain, hiding a chain that clients without that intermediate reject.
**Trade-off.** A certificate that only strict validators refuse is reported as valid.

### ADR-3 — The reason comes from the verification code, not the message

**Decision.** Map `verify_code` (numeric, `X509_V_ERR_*`) to the reason; keep `verify_message` as
the free text.
**Alternatives.** Match words in the message.
**Why.** The codes are part of the OpenSSL API and stable across versions; the messages are
English prose that can change wording.
**Trade-off.** A new code lands in `other` until the table names it; the message still tells the
user what happened.

### ADR-4 — Test certificates are made at run time with `trustme`

**Decision.** Add `trustme` and `cryptography` to the dev group. `trustme` makes the CA, the
intermediate and the leaves with chosen names and dates; `cryptography`, already its dependency,
makes the two certificates `trustme` has no option for.
**Alternatives.** (a) Certificates committed to the repository. (b) The `openssl` command line.
(c) `cryptography` alone.
**Why.** Committed certificates have fixed dates: "expires in 10 days" cannot exist in a file,
and every valid one turns into an expired one some day. The `openssl` command is not the same
program, or not present, across the Linux and Windows runners. `trustme` does the common case in
one line, with typed APIs, and is maintained by the `python-trio` project.
**Trade-off.** Two more dev packages in the lock; the runtime package still declares none
(RNF-01), which the CI `package` job keeps checking.

### ADR-5 — The network guard is a fixture of the suite, not a plugin

**Decision.** An autouse fixture in `tests/conftest.py`, on the standard library, wraps the two
calls every connection passes through.
**Alternatives.** `pytest-socket`, which blocks sockets with an allow list of hosts.
**Why.** The rule is narrow (resolve only loopback names, connect only to loopback addresses), it
fits in a few dozen lines that the suite tests itself, and it adds nothing to the lock.
**Trade-off.** Code that bypasses `socket` (a C extension opening its own sockets) would not be
caught; nothing in this project does that.

### ADR-6 — The timeout bounds the connection and each handshake step

**Decision.** The socket timeout given to `create_connection` applies to the connection and to
every read and write of the handshake. Name resolution uses the system resolver without a
TLSVigil timeout.
**Alternatives.** (a) Run the check in a thread with an overall deadline. (b) Resolve names with a
custom DNS client.
**Why.** A thread that misses its deadline cannot be stopped and keeps the socket open; a DNS
client is a dependency or a protocol implementation, against ADR-1 of spec `001`. The system
resolver has its own timeouts.
**Trade-off.** The wall time of one check can exceed `timeout`: a name with several addresses can
time out once per address, and a slow resolver adds its own delay.

### ADR-7 — The trust store is the system's, and the context is an argument

**Decision.** The check trusts what `ssl` loads from the system (OpenSSL's default paths on Linux,
the Windows certificate stores on Windows); `context` is a parameter used by the tests.
**Alternatives.** Ship or require a CA bundle (`certifi`), or add a configuration key for one.
**Why.** A bundle is a dependency (ADR-1 of spec `001`), and the system store is what the other
clients on that machine trust. A configuration key for a private CA is not part of this spec.
**Trade-off.** The verdict depends on the trust anchors of the machine. RNF-02 holds for what the
check sets; Windows loads intermediates from its `CA` store as trusted, so a chain that a Linux
runner reports as `untrusted` can verify on a Windows machine that has the intermediate cached.

## Test strategy

- **Against the local server** (`test_certificate.py`), with `client_context`:
  - verified: 90 days, `N` days plus one hour (days left `N`), two hours (`0`); issuer names read;
    an IP certificate checked as `127.0.0.1`;
  - invalid: expired (`not_before` 30 days ago, `not_after` yesterday), not yet valid (`not_before`
    tomorrow), issued for `other.test` and checked as `localhost`, issued for `localhost` and
    checked as `127.0.0.1`, self-signed, signed by a second CA the context does not trust, leaf
    sent without its intermediate; each asserts the reason, a non-empty message, and that
    `days_left` and `not_after` are `None`;
  - a leaf without an Authority Key Identifier verifies (ADR-2);
  - error: a port taken from a socket that was bound and closed (`refused`; timeout 5 s, because a
    refused connection on Windows loopback takes about two seconds), the `silent` server with a
    timeout of 0.2 s (`timeout`), the `plain` server (`tls`), and a name that does not resolve,
    with `socket.getaddrinfo` patched in that test to raise `gaierror` (`dns`);
  - TLS 1.1: a server limited to TLS 1.1 (`@SECLEVEL=0`) is first reached by a client context
    that allows TLS 1.1, as the positive control (skipped when the platform cannot complete that
    handshake); then `check_certificate` with `create_context()` gives `error` `tls`. The
    deprecation warnings `ssl` raises for TLS 1.1 are caught in that test only;
  - one connection: the server counts accepted connections, and an `invalid` check leaves the
    count at `1`;
  - validation: a parametrized table of bad hosts, ports, timeouts and a naive `now`, each raising
    `ValueError` before any socket is created (the guard's connect wrapper records calls, and the
    count stays `0`), with a valid call as the control.
- **Pure** (`test_classify.py`): `days_left` `N - 1`, `N`, `N + 1`; threshold `0`; a negative
  threshold; `invalid` and `error` with any threshold.
- **Guard** (`test_network_guard.py`): resolving `localhost` and connecting to the local server
  succeed (positive control); resolving `example.com` and connecting to `192.0.2.1` and
  `2001:db8::1` (documentation addresses) raise `NetworkAccessError`, which proves the wrapper,
  not the network, answered.
- **Deterministic dates:** each test takes `now = datetime.now(UTC)` once, builds the certificate
  relative to it and passes the same `now` to the check (RNF-04).
- **Seen failing:** before each test is trusted, the line it guards is broken once: the `max(0,
  …)` removed, a code moved to another reason in the table, `VERIFY_X509_STRICT` left on (seen on
  Python 3.13 or newer), the minimum version set to TLS 1.1, `except TimeoutError` deleted, the
  validation of `:` removed, the guard's allow list widened to every address. Each sabotage and its
  red run go into the tasks and the pull request.
- **Coverage:** `src/tlsvigil/certificate.py` at 100% lines and branches; any branch only one
  platform reaches is marked and explained in the code.

## Deviations

1. **RF-07, ADR-5: the guard is its own module.** The rules, `NetworkAccessError` and
   `NetworkGuard` live in `tests/network_guard.py`, and `conftest.py` only installs them through
   the autouse `network_guard` fixture. The tests import `NetworkAccessError` from that module,
   because importing `conftest.py` directly is unsupported by pytest. The guard also records
   every lookup, not only every connect, so a test can assert that nothing was resolved.
2. **RF-06: the timeout must also be finite.** `float("inf")` and `nan` are refused with the
   other bad timeouts: `nan` already fails `> 0`, and `socket.settimeout(inf)` raises
   `OverflowError`, which is not an `OSError` and would escape the check instead of becoming a
   result. The type rules use `type(x) is int` (and `str`, `float`) rather than `isinstance`, which
   refuses a `bool` in one test and keeps `mypy --strict` free of redundant expressions; an aware
   `now` is one whose `utcoffset()` is not `None`.
3. **RF-02, ADR-1: `classify` checks more than the threshold.** It refuses a `float` or `bool`
   threshold as well as a negative one, checks the threshold before the outcome (so a bad
   configuration fails on every host, not only on the verified ones), and refuses a verified
   result without days left with `ValueError`. The check never builds such a result; the guard
   is for one built by hand.
4. **RF-07: the `serve` fixture takes a `configure` hook.** `start(leaf, configure=...)` changes
   the server context before the server starts; the TLS 1.1 test uses it to limit the server to
   TLS 1.1 at `@SECLEVEL=0`. The other tests leave it out.
5. **RF-01, RNF-03: the common name is read from a trusted self-signed leaf.** A `trustme` CA names
   an organization and a unit but no common name, so the issuer test of a `trustme` chain reads
   the organization (and no common name), and a self-signed leaf added to the context as a trust
   anchor gives a common name with no organization.
6. **RF-04, RF-08: three failures are injected.** Loopback never times out on connect, is never
   unreachable, and a verified handshake always carries `notAfter` and an issuer, so these tests
   patch `socket.create_connection` (a `TimeoutError`, an `OSError` with `ENETUNREACH`) or
   `ssl.SSLSocket.getpeercert` (no `notAfter`, no issuer). The paths they reach are the
   `except` branches and the guards of the flow above; the real handshake still runs in the
   `getpeercert` cases.
7. **RF-07: `LocalServer` also listens on `::1`.** `localhost` resolves to `::1` first on many
   machines; with a listener on `127.0.0.1` only, each check of `localhost` was first refused on
   `::1`, which on Windows costs about two seconds (42 s for the suite of this stage). The server
   now binds `::1` on the same port when the machine has IPv6, accepting on both through
   `selectors`; when that bind fails, the tests still pass, only slower. `host` stays
   `127.0.0.1`, and the counter counts the connections of both addresses.

## Implementation notes

- **Suite:** 101 tests, 86 of them new in this spec (63 for the check, 13 for the
  classification, 10 for the network guard), with no test skipped on Windows and Python 3.15.2:
  the TLS 1.1 positive control completes its handshake there. `src/tlsvigil` stays at 100% of
  lines and branches, with no branch excluded.
- **Time:** the suite runs in 5.9 s and the full local gate (ruff, black, mypy, pytest) in 8.2 s,
  on Windows and Python 3.15.2. The listener on `::1` (deviation 7) is what keeps the suite under
  ten seconds there.
- **No command calls the check:** `tlsvigil --version` is still the only command that
  runs; spec `004` connects `check_certificate` and `classify` to the configuration and the output.
